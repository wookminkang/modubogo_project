# GEO 체크 (`/geo-check`)

ChatGPT에 키워드를 물었을 때 **우리 병원이 답변에 등장하는지 O/X로 측정**하는 영역.
`/site-analysis`(사이트가 AI에게 잘 보이게 되어 있나 진단)의 후속으로, 이쪽은 **실제로 보이고 있나**를 잰다.

## 절대 어기면 안 되는 규칙

**답변 수집 호출에 병원명을 넣지 않는다.** `askChatGpt()`에는 키워드 원문만 넘어간다.
"리움한방병원 나오는지 봐줘" 식으로 물으면 모델이 힌트를 받아 언급해버려 측정 자체가 무의미해진다.
판정은 `judgeAnswer()` 별도 호출에서 한다. 이 분리를 깨는 수정은 리뷰에서 최우선으로 막을 것.

**`getRunProgress()`에 `revalidatePath()`를 넣지 않는다.** 서버 액션 revalidation이 실행 중인
액션과 큐잉되어 진행률 폴링이 멈춘다. CRUD 액션에만 붙인다.

## 구조

```
page.tsx                   대상 병원 목록 + 최근 노출률/델타
[targetId]/page.tsx        체크리스트 본문 (maxDuration=300)
_components/
  TargetForm.tsx           대상 등록 (병원명·별칭·지역)
  RunPanel.tsx             실행 + 진행률 폴링 + 요약 밴드
  ChecklistTable.tsx       O/X 표, 행 펼치면 답변 원문·인용 출처
  KeywordManager.tsx       키워드 여러 줄 등록 / 활성 토글 / 삭제
```

관련 lib (`src/lib/`):

| 파일 | 역할 |
| --- | --- |
| `geo-db.ts` | 쿼리 레이어. **read는 폴백, write는 throw** (db.ts와 다른 점 — 결과 저장 실패를 삼키면 디버깅 불가) |
| `geo-match.ts` | 코드 기반 O/X 판정. 순수 함수만, 외부 의존 0 |
| `geo-openai.ts` | 수집(`web_search`)·판정(structured output) 호출 분리 |
| `geo-actions.ts` | 서버 액션. 워커풀 실행·병합 판정 |

스키마 (Supabase SQL 에디터에서 순서대로 수동 실행):
`sql/geo_check.sql` → `sql/geo_check_category.sql`(분류·비고) → `sql/geo_check_site.sql`(공식 홈페이지 인용)

## 점검 단위는 "하루에 한 번"

회차 개념은 없다. 날짜(한국 기준)가 단위이고, 화살표로 하루씩 이동한다(`?date=YYYY-MM-DD`).
- 같은 날 여러 번 돌리면 **그날의 최신 실행**을 그날 결과로 본다 (`getGeoRunDetailForDate`)
- **점검은 오늘 날짜에만** 실행할 수 있다 — 지난 날짜를 소급해 채우는 건 말이 안 되므로 UI에서 버튼을 숨긴다
- 점검 안 한 날도 표는 뜬다. 그날 칸이 전부 공란이고 그게 "미점검"이다

표는 결과가 아니라 **키워드 전체**를 기준으로 그린다. 실행 후 추가한 키워드도 행은 있어야 하고
그 칸이 공란이 된다 (실수했던 부분 — 결과 기준으로 그리면 새 키워드가 안 보인다).

## O/X 판정 방식

세 가지를 OR 로 합친다:

```
found = 코드 문자매칭  OR  LLM 판정  OR  공식 홈페이지 인용
```

셋째가 중요하다 — 답변 본문에 이름이 없어도 ChatGPT 가 `geo_targets.site_domains` 의
도메인을 출처로 인용했다면 그것도 노출이다 (`citesOwnSite`, 서브도메인 포함).

코드 매칭과 LLM 판정은 **둘 다 항상 돌리고 둘 다 저장**한다.
두 판정이 엇갈리거나 fuzzy 매칭이면 `needs_review=true`로 화면에 ⚠를 띄운다.

- `geo-match.ts` — NFKC 정규화 후 공백·구두점을 지우고 비교. ① 정식명 ② 별칭 ③ 핵심토큰+유형접미사(간격 3자, 비의료 어휘 차단)
- `geo-openai.ts` — 답변 텍스트 안에서만 판단하도록 지시. 모델이 인용한 문구가 실제 답변에 없으면 환각으로 보고 검토 대상으로 넘김

**`aliases`가 정확도의 실질적 손잡이다.** 오탐/미탐 대부분은 별칭 하나 추가로 해결된다.

답변 원문(`answer_text`)과 인용 출처(`citations`)를 저장하는 이유는 판정 로직을 고쳐도
API 재호출 없이 과거 데이터를 재판정할 수 있게 하기 위함이다. 판정 규칙을 바꿀 땐 이 점을 활용할 것.

## 실행 전략

Vercel `maxDuration=300`이 절대 제약이라 순차 실행은 키워드 10개만 넘어도 타임아웃난다.

1. `startGeoRun` — run 1행 + 키워드 수만큼 결과 행을 `pending`으로 **미리 삽입**하고 runId 즉시 반환
2. `executeGeoRun` — 동시성 4 워커풀. 키워드별 60초 타임아웃, 전역 260초 예산
3. 예산 초과·강제 종료 시에도 완료분은 DB에 남고 남은 `pending`이 보인다 → "미완료만 재실행"이 성공분에 비용을 다시 쓰지 않음

동시성을 4로 둔 이유: `web_search`는 자체 레이트리밋이 있어 올릴수록 429로 오히려 느려진다.

## 주의점

- **지역 키워드는 구체적으로.** "둥촌동 요양병원 추천해줘"는 ChatGPT가 서울 둔촌동으로 알아듣는다.
  `geo_targets.region`을 `user_location` 힌트로 넘기지만 그것만으로는 부족하니 키워드에 "광주 둥촌동"처럼 명시하게 안내한다.
- 측정 대상은 chatgpt.com 화면이 아니라 **OpenAI API + web_search** 결과다. 근사치로는 충분하지만 100% 동일하진 않다.
  광고주 리포트로 내보낼 땐 이 점을 표기할 것.
- 모델은 `geo-openai.ts` 상단 `COLLECT_MODEL`/`JUDGE_MODEL` 상수로 관리한다. 수집은 ChatGPT 사용자 경험에 가까운 `-chat-latest` 계열을 쓴다.

## 결과가 매번 흔들린다 (중요)

같은 키워드를 34분 간격으로 두 번 돌렸더니 O 가 X 로 뒤집힌 사례가 실제로 있었다.
web_search 가 그때그때 다른 페이지를 물어오고 생성도 확률적이라, **1회 측정은 노이즈가 크다.**

그래서 답변 원문(`answer_text`)과 인용(`citations`)을 실행마다 통째로 스냅샷해 둔다.
나중에 "그때 왜 X였지"를 되짚을 수 있고, 판정 로직을 고쳐도 재판정할 수 있다.

날짜별 변화(▲▼)를 해석할 땐 이 흔들림을 감안해야 한다. 신뢰도를 올리려면
하루 N회 반복 후 다수결/노출률로 집계하는 방식을 검토할 것 (스키마는 이미 담을 수 있다).
